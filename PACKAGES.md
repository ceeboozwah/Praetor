# PACKAGES.md — registry/dependency contract (N60A)

Status: **N60B+N60C implemented** — everything in this document works
against a directory registry today (`compiler/tests/registry.rs`
pins each adversarial case). Remote transport remains deferred.
This document freezes the semantics the package system provides. It
extends the existing `project.toml`/`project.lock`/path-dep machinery
(`project.rs`) rather than replacing it. No server exists; the
registry is defined as a directory layout so the entire contract is
exercisable offline.

The governing constraint is the same as everywhere else in this
project: no hidden state, no hidden I/O, no surprises. Resolution is
deterministic, the lockfile is authoritative once written, and every
integrity claim is checkable from bytes on disk.

## 1. Package identity

A package is identified by **`name` + `version`**.

- `name` matches `[a-z][a-z0-9_]{0,63}` — lowercase, no separators,
  no namespaces in v1. `std`, `core`, `our`, and `self` are reserved
  (`std` already is).
- `version` is strict semver `MAJOR.MINOR.PATCH` — digits only, no
  prerelease or build metadata in v1.
- The package root contains `project.toml` with `[project] name` +
  `version`, and `src/` as its module root — identical to a path
  package today. A registry package IS a path package that arrived
  via a different source; `import name.mod` semantics are unchanged.
  Module boundaries remain naming/loading boundaries, not safety
  boundaries — a dep's modules are checked exactly as own code.
- **Module leaf names are globally unique across the dep graph.**
  `import a.util` and `import b.util` both introduce the `util`
  qualifier — code writes `util.f()`, so the loader rejects two
  same-named files rather than guess. Package authors pick distinct
  module names; fully-qualified usage (`a.util.f()`) is a
  language-level change deferred indefinitely.

## 2. Dependency declarations

`[dependencies]` values gain one grammar production — an inline table:

```toml
[dependencies]
lib    = "1.2"                          # registry: caret req
exact  = "=1.2.3"                       # registry: pinned
local  = { path = "../lib" }            # path: existing form
pinned = { path = "../lib", version = "1.2" }  # path + version check
```

- A bare string is a registry **version requirement**.
- `{ path = "..." }` is a local path dep — today's semantics.
- `{ path, version }` additionally asserts the dep's manifest version
  matches the req — mismatch is a resolve error, not a warning.
- Declaring both a string req and a `path` for the same name is
  impossible by construction (one table row). Overriding a transitive
  dep is done by declaring a `path` for that name in the top-level
  manifest; it is accepted only if the path dep's version satisfies
  every transitively-declared req for that name.

## 3. Version requirements

**v1 grammar is exactly three forms — nothing else parses:**

| req       | meaning                                     |
|-----------|---------------------------------------------|
| `1.2.3`   | `^1.2.3` — compatible (cargo convention)    |
| `^1.2.3`  | `>=1.2.3, <2.0.0`; `^0.2.3` → `<0.3.0`; `^0.0.3` → `<0.0.4` |
| `=1.2.3`  | exactly 1.2.3                               |

No comparators (`>=`, `<`), no `*`, no `||`, no prerelease in v1 —
a partial parser must never look like full semver support. `1.2`
pads to `1.2.0` for comparisons. Requirements evaluate against the
index's version list — the resolver picks the **highest satisfying
version** (comparator conjunctions may return later; the evaluators
will share `Req` machinery).

## 4. Resolution

- One version per package name globally. Diamond reqs are AND-ed;
  if the intersection is empty, resolve fails naming the chain.
- Resolution consults the index for version lists; `yanked = true`
  versions are excluded **unless already present in the lockfile**
  — a yank never invalidates a locked, buildable set (cargo's rule,
  frozen explicitly: the lock is the reproducibility artifact, the
  index yank flag only gates *new* selection).
- The resolver never revises a picked version: the first-declared
  req selects the version; later transitive reqs for the same name
  must be satisfied by the pick or resolution fails naming the
  chain (and suggesting a top-level pin). One pass, loud failure,
  no backtracking — v1 deliberately has no solver.
- Cycles are rejected — the existing `stack` check extends to
  registry deps unchanged.
- `requires` (see §6) filters versions before selection: a version
  whose toolchain req excludes the running `ourc` is invisible.
- Resolution writes `project.lock` only when the resolved set
  changed; `our build`/`test`/`run`/`check` all resolve.

## 5. Lockfile

`project.lock` extends its current shape:

```toml
# project.lock — generated by `our`, do not edit
[lock]
format = 2             # format gate — VERSIONING.md §4
tool = "ourc 0.2.0"

[dep.lib]
source = "registry"
version = "1.2.3"
sha256 = "ab12…"          # canonical tree hash — see §6

[dep.local]
source = "path"
path = "../lib"
sha256 = "cd34…"          # same hash, computed over the live tree
```

- The lock is authoritative: if it satisfies the manifest, its
  versions are used verbatim (`--locked` errors if it wouldn't).
- Path-dep hashes upgrade from FNV-1a to SHA-256 — same field role
  (drift detection), now collision-resistant. The `hash =` key is
  renamed `sha256 =`; old locks are stale by tool-version check.
- A path dep's hash is recomputed each resolution — drift between
  lock and disk is reported by `our deps` as today.

## 6. Registry layout (v1: a directory)

A registry is a directory — `OUR_REGISTRY` env var or the default
`registry/` next to the repo for development:

```
registry/
  index/
    lib.toml                # one file per package name
  src/
    lib/1.2.3/              # unpacked package trees
      project.toml
      src/…
```

`index/lib.toml`:

```toml
[[version]]
version = "1.2.3"
sha256 = "ab12…"            # canonical tree hash
requires = "0.9"            # ourc toolchain req — same v1 grammar
yanked = false
```

**Canonical tree hash**: SHA-256 over the concatenation of
`relpath \0 filebytes \0` for every file under the package root in
lexicographic order, excluding `.git/` and `build/`. `tests/` IS
included — tests ship in the package; they're hashed but never
built for deps. SHA-256 is implemented in-tree — zero external
deps is a project invariant.

**Trust model**: the index is the source of truth for version
lists and hashes; the cache content is verified against the index
hash before use. Transport security (HTTPS, signing) is deferred —
a directory registry is trusted by construction. A remote index
later inherits this exact contract over HTTPS.

## 7. Cache and offline builds

```
$OUR_HOME/registry/<name>/<version>/   # default ~/.our/registry/
```

- First resolve of a registry dep: verify the unpacked tree against
  `index[name]`'s sha256, copy to cache, use from cache.
- Cached trees are verified once per resolution — the sha256 is
  cheap relative to a compile, so there is no "trust a stale cache"
  path.
- `our build --offline`: never read the index; resolve entirely from
  the lockfile + cache. A missing cache entry is an error.
- With a complete lock + warm cache, `our build` performs zero
  index/registry I/O — reproducible offline builds by construction.

## 8. Publishing (contract only — `our package` deferred)

`[project]` gains optional metadata: `description`, `license`,
`repository`. A publishable package requires name + version +
license. "Publishing" to a directory registry is: `our package`
verifies the manifest, computes the canonical tree hash, appends a
`[[version]]` entry to `index/<name>.toml`, and copies the tree to
`src/<name>/<version>/`. Version must not already exist — immutable.
`yanked = true` is set by hand-editing the index (server-side yank
API deferred with the server).

## 9. Failure classes (first-run checklist)

| phase   | failure mode                                     |
|---------|--------------------------------------------------|
| parse   | malformed manifest req / bad version literal     |
| resolve | no satisfying version / empty intersection / cycle |
| index   | package absent / all versions yanked / requires  |
| cache   | tree hash mismatch vs index                      |
| lock    | --locked drift / stale tool version              |
| fs      | unreadable registry dir / cache write failure    |

Each is a distinct diagnostic class — resolution bugs must never
surface as I/O errors or vice versa.

## 10. Remote transport (N60C)

A remote registry changes **where bytes come from, nothing else**.
`OUR_REGISTRY` may be an `http(s)://` base URL instead of a
directory; the same layout is served over GET:

```
GET <base>/index/<name>.toml                  — the index file
GET <base>/src/<name>/<ver>/<relpath>         — one package file
```

- Index format is identical, plus one required-for-remote key per
  `[[version]]` entry: `files = ["project.toml", "src/util.lang", …]`
  — the canonical relpath list (a directory registry ignores it and
  walks the tree; a remote registry needs it because you can't list
  a directory over GET).
- Acquisition: fetch every `files[]` member into a scratch tree,
  compute the canonical SHA-256 locally, compare to the index's
  `sha256`, then promote into the same `$OUR_HOME/registry` cache a
  directory registry uses. The verified-cache path is byte-for-byte
  identical from there — resolution, lockfiles, `--offline`, and
  `--locked` never learn the difference.
- Transport is `curl -fsSL` — zero crate deps is a project
  invariant, and `curl`/`curl.exe` is universal on macOS, Linux, and
  Windows 10+. HTTPS is the transport's problem; integrity is the
  tree hash's. A TLS-free `http://` base is accepted for
  localhost/LAN development (the hash still verifies content).
- Once cached, a dep is purely local: warm cache + lockfile means
  zero network — the remote story degrades gracefully to §7's
  offline semantics.

## 11. Deferred

- Namespaces/ownership, signing, auth — server concerns.
- `[dev-dependencies]`, feature flags, target-specific deps.
- `our vendor` (copy deps into the project tree) — cache is enough.
- Prerelease versions, `||` ranges, multiple sources per name.
- `our add`/`our remove` manifest editing — manifests are hand-edited
  until the grammar settles.
- Retry/resume/mirror-fallback transport policy — `curl -fsSL`
  failures surface as-is in v1.
